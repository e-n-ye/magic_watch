# Stage 00：直接调用

## 新需求与约束

实现 Heart、Steps 两张卡。点击卡片进入对应详情，点击 Back 返回首页。

当前只有鼠标、单 View 和同步执行。不要求跨平台、异步事件或脱离 LVGL 测试。

## 当前调用链与状态所有权

当前预期链路：

```text
LVGL CLICKED
-> 卡片 callback
-> show_detail(feature)
-> 直接修改 LVGL 对象
```

详情内容和页面显隐暂时都由 `app_direct.c` 持有。这里没有 Core、Adapter 或事件队列。

## 第一次实际观察

已验证：

- Heart 点击进入 Heart Detail 正常。
- Steps 点击进入 Steps Detail 正常。
- Back 返回首页正常。

代码事实与事前预测的差异：

- 当前没有全局“页面枚举”。首页和详情由两个 panel 的 `HIDDEN` 标志直接表示。
- 当前没有保存 `current_feature`。`feature` 只在 `show_detail()` 当次调用中决定标题，之后没有行为需要再次读取它。
- 因此“可能以后需要”还不足以证明现在应该保存状态。
- “应用逻辑不复杂”方向正确，但可以进一步具体化为：单输入源、同步调用、单 View 所有者、没有跨平台共享规则，也没有脱离 LVGL 测试的要求。

这不是给事前预测判对错。事前预测的作用是让我们看到：哪些状态只是凭感觉想象出来的，哪些状态已经被后续行为真实读取。

## 第一个真实缺陷：拖动后误激活

复现：

```text
在卡片上按下鼠标
-> 按住并拖动到别处
-> 松开
-> 仍可能触发卡片 CLICKED
```

初步分类：

- 这是输入激活规则与产品期望不一致。
- 它发生在 `LVGL pointer -> LV_EVENT_CLICKED -> callback` 之间。
- 它不是页面导航规则、数据模型或异步顺序问题。
- 当前证据不能证明需要 EventQueue、Coordinator 或 Adapter。

LVGL 提供的是通用 `CLICKED` 事件，产品需要的是更严格的 tap-only：

```text
按下位置有效
并且移动距离未超过阈值
并且松开时仍满足激活条件
```

### 候选方案

方案 A：暂时接受 LVGL 默认语义。

- 改动最少。
- 适合只验证页面直接调用链的短期实验。
- 缺点是已知误触继续存在。

方案 B：在 Stage 00 View 内增加局部 tap guard。

- 只为三个按钮记录按下、移动和释放是否仍可视为 tap。
- 能解决当前可观察缺陷。
- 会给 `app_direct.c` 增加输入状态和阈值，使原本简单的 View 开始承担输入策略。

方案 C：建立通用 Input Port 或激活策略层。

- 可以统一未来鼠标、触摸和其他 pointer 输入。
- 当前只有鼠标和一个 View，成本明显更高。
- 现在选择它会受到 Magic Watch 既有实现的答案污染。

### 我的选择

- 我选择：方案 B，在 Stage 00 View 内增加局部 tap guard。
- 选择依据：当前只有一个 View 和三个按钮，局部过滤已经能覆盖实际观察到的误触，不需要先建立通用输入层。
- 我认为这个问题属于哪一层：问题产生于 LVGL 的默认点击语义与产品需要的 tap 语义不同，应在点击进入页面逻辑之前的输入激活边界拦截。
- 我暂时不选择其他方案的原因：方案 A 会保留已复现的缺陷；方案 C 对当前单 View、单 pointer 输入规模过大，也会把 Magic Watch 的既有答案提前灌入实验场。
- 如果以后出现什么新需求，我会重新考虑更大的方案：多个 View 都重复实现相同过滤，或者鼠标、触摸等多个 pointer 来源需要遵守同一套激活规则。

术语校准：

- 初始化只负责注册 LVGL 回调，不是误触发生的位置。
- 真正的语义转换发生在一次 `PRESSED -> PRESSING -> RELEASED` 被接受为页面激活的过程中。
- 因此这里说的“逻辑层入口”，具体是 View callback 进入 `show_detail()` / `show_home()` 之前，而不是页面导航逻辑内部。

### 方案 B 实现记录

- View 只保存一份当前 pointer 会话状态：按下对象、按下起点、跟踪状态和是否发生明显移动。
- Heart、Steps、Back 的 callback 都先调用同一个 `tap_guard_accept()`；只有它确认释放为有效 tap，页面动作才继续。
- 移动横向或纵向超过 `12 px`，或者收到 `PRESS_LOST`，本次按压不再激活页面动作。
- 状态和阈值仍留在 `app_direct.c`，没有抽成 Input Port、Adapter 或共享策略。

这次改动带来的直接代价：

- 原本只监听 `LV_EVENT_CLICKED` 的 View，现在需要理解四种 pointer 事件。
- 三个简单页面 callback 前增加了同一个状态过滤入口。
- 如果后续第二套 View 也复制这段规则，重复本身才会成为考虑更大边界的新证据。

实现修正：

- 第一版为三个按钮各分配一份 `tap_guard_t`，把“控件数量”误当成了“同时存在的 pointer 会话数量”。
- 当前 runtime 只有一个 pointer，同一时刻只会有一次活动按压，因此动态状态收敛为一个 View 级 `s_tap_guard`。
- 每个控件仍需注册自己的 callback，因为有效 tap 之后执行的页面动作不同；这是行为绑定，不是三份手势状态。

人工验证结果：

- Heart、Steps、Back 正常轻点有效。
- 少量移动不会过滤正常点击。
- 按下后明显拖动或拖出按钮再松开，不会激活页面动作。

`12 px` 只是本 Stage 的实验参数，不代表可跨设备复用的产品合同。

## Stage 00 复盘

### 为什么直接调用足够

当前页面足够轻薄，每个按钮都有确定且唯一的页面语义。callback 可以同步调用 `show_detail()` 或 `show_home()`，没有第二个状态所有者、异步来源或跨平台规则需要协调。因此，直接调用已经足够表达当前导航行为。

### tap guard 的收益与代价

收益：

- 把 LVGL 的通用 pointer 事件收紧成当前产品需要的 tap-only 激活语义。
- 已实际消除“按下后拖动再松开仍激活”的误触。

代价：

- 每个页面 callback 都必须先调用 `tap_guard_accept()`，开发者以后可能漏写。
- View 开始持有输入状态和阈值，并理解四类 pointer 事件。
- 当前实现解决了缺陷，但还不是“注册一次后所有激活自动变干净”的理想过滤器模块。

### 为什么暂不建立 Input Port

当前只有一个 View、一个 pointer 来源和三个按钮。建立通用 Input Port 会增加新的接口、文件和调用层，却还没有第二个消费者证明这份共享策略确实存在。当前保留局部方案，但把“callback 容易漏接 guard”记录为未消失的维护风险。

### 我高估、低估和仍未掌握的部分

- 事前认为全局页面变量和 `current_feature` 必然需要。当前代码证明页面显隐和详情标题暂时可以直接由 LVGL 对象表达；这不代表显式状态永远不需要，只说明本 Stage 尚无行为会读取它。
- 低估了“点击”也包含按下、移动、释放、阈值和取消规则，不只是一个瞬时 callback。
- 目前仍缺少类似平衡车“传感器 -> 控制环 -> 执行器 -> 反馈”那样清晰的 UI 系统蓝图。Stage 00 当前能确认的最小闭环是：

```text
用户 pointer 操作
-> LVGL 产生 pointer 事件
-> tap guard 判断是否为有效激活
-> callback 选择页面动作
-> show_home()/show_detail() 修改 LVGL 对象
-> 用户看到页面变化
```

这个闭环只解释当前单 View 同步 UI，不等于最终产品架构。

## 冻结决定

Stage 00 冻结并保留：

- 保留直接 callback 页面导航。
- 保留 View 局部、单状态的 tap guard。
- 延迟显式 PageState、`current_feature`、Input Port、EventQueue、Coordinator 和 Adapter。
- 不把当前 tap guard 视为最终模块；以后必须由真实的重复、漏接或多输入需求决定是否扩大边界。

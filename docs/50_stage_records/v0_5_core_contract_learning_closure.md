# V0.5 Core 合同学习收口与 V0.6 交接

> 状态：Current Stage Record  
> 更新日期：2026-06-13  
> 路由类型：阶段记录  
> 适用场景：回顾 `V0.5` 真正完成了什么，理解为什么旧 `V0.5-A~G` 路线已过时，以及确认 `V0.6` 从哪里开始

---

## 1. 一句话结论

`V0.5` 不是“从零造一个 core”的阶段，而是把已经存在但边界松散的共享语义合同收口成可测试、可解释、可交接的阶段。

它最后建立的是：

- `UiEvent -> watch_core -> PageState / PageIntent / Snapshot` 的共享导航合同
- `Request -> Action -> commit` 的最小 Power 合同
- PC / F411 Adapter 的统一消费规则
- `Input Port / Adapter / Lite View / Platform Port` 的清晰边界

`V0.6` 因此不再从新增 core 名词开始，而是从平台 Action executor 和真实亮灭屏 / 唤醒执行闭环开始。

---

## 2. 为什么旧 `V0.5-A~G` 路线已经过时

旧 `V0.5-A~G` 的出发点，是把 `EventQueue`、`Coordinator`、`Snapshot`、页面状态和 Power 控制近似看成“待从零实现”的空白骨架。

后续代码和审计证据已经证明，这个前提不成立：

- `watch_core` 里已经存在共享事件队列、最小 Coordinator、`UiModelSnapshot` 和基本导航链路。
- F411 当前活跃主链已经是 `Input Port -> F411UiAdapter -> watch_core -> F411UiAdapter -> Lite View`。
- 真正的缺口不是“有没有这些模块”，而是“这些模块的权威边界、公开合同和平台消费规则是否足够清楚”。

因此，继续按旧 `V0.5-A~G` 机械推进，会产生三个问题：

1. 重复造已有模块，把“收口”误做成“重写”。
2. 让平台重新拥有业务语义，反而破坏刚建立的共享合同。
3. 把学习重点从“状态所有权和边界判断”滑回“名词越多越像架构”。

所以当前 `V0.5` 的真实价值，不是继续造新结构，而是把已经可运行的结构收成稳定合同。

---

## 3. 当前 `V0.5` 实际完成了什么

### 3.1 `P0`：先证明和审计，而不是先改代码

- 给 `watch_core` 增加了纯 PC 合同测试护栏。
- 审计出 F411 当前新旧主链的真实所有权。
- 抽取真正的 `F411UiAdapter`。
- 让旧 `watch_event_queue.*` / `watch_screen_manager.*` 退出当前 MDK target。

这一轮的学习重点是：不要因为旧模块名字还在，就误判它们仍是当前运行主链。

### 3.2 `P1`：把页面状态、页面动作和 Adapter 消费规则拆开

- `WatchCorePageState` 成为权威当前页面状态读取合同。
- `PageIntent` 被收口为瞬时页面动作，而不是权威当前页。
- 单次外部输入后的共享处理规则，统一为 `process_pending_events()` drain 到稳定态。
- PC 与 F411 Adapter 都改成消费这套合同，不再自己猜首页。

这一轮的学习重点是：持久状态和瞬时动作不是同一层东西，不能混着用。

### 3.3 `P2`：把“处理完成”语义收紧到队列空

- 修正了 `watch_core_process_pending_events()` 的真实结束条件。
- 明确区分：
  - 事件被消费
  - 是否产生页面动作
  - 队列是否已经空
- 输出第三 Adapter 的最小接入门。

这一轮的学习重点是：`no-op` 不是 bug，但不能被误当成“整轮处理已经完成”。

### 3.4 `P3`：建立最小 Power 共享合同，但不越权做平台执行

- 先用文档决策锁定 `SCREEN_ON / SCREEN_OFF` 双状态。
- 明确采用 `Request -> Action -> Platform apply -> commit` 两阶段合同。
- 在 `watch_core` 中实现最小 `PowerState / PowerRequest / PowerAction / commit` 合同。
- 审计确认页面状态机和 Power 状态机仍是两个独立状态机。

这一轮的学习重点是：Core 负责决策，平台负责执行，失败不能伪装成成功。

### 3.5 `P4`：把学习路径和阶段交界写清

`P4` 的任务不是加新功能，而是防止后续窗口重新退回过时理解：

- 把旧 `V0.5-A~G` 改写为历史学习假设，而不是当前执行路线。
- 把当前 `V0.5` 的真实完成面收口成阶段记录。
- 明确 `V0.6` 从平台执行闭环开始。

---

## 4. `V0.5` 最终建立的稳定合同

当前已经稳定成立的共享语义包括：

- `UiEvent` 是共享输入语义入口。
- `watch_core` 拥有共享 UI 事件队列、最小 Coordinator、`UiModelSnapshot`、页面状态和最小 Power 状态。
- `WatchCorePageState` 是权威当前页面状态。
- `PageIntent` 只表示瞬时页面动作。
- `PowerRequest` 表示请求，`PowerAction` 表示待平台执行的动作，`commit` 才迁移持久 Power 状态。
- 单次输入后由 Adapter 统一 drain 到稳定态，再按最终 `PageState + Snapshot` 同步 View。
- Platform Port 可以执行动作，但不是业务策略源。

这些合同已经足以支撑第三个平台继续接入，而不需要再先发明新的 Core 名词。

---

## 5. `V0.5` 明确没有完成什么

为了避免把阶段总结写成“什么都做完了”，这里明确保留未完成项：

- 还没有真实平台 `PowerAction` executor。
- 还没有背光、亮灭屏门控或真实唤醒执行代码。
- 还没有 LILYGO 平台接入。
- 还没有把表冠输入在熄屏态下接入真实 Power 执行闭环。
- 还没有进入更大页面扩张、更多手势统一或产品化 UI。

这些不是 `V0.5` 失败，而是被明确留给 `V0.6` 的执行层问题。

---

## 6. `V0.6` 从哪里开始

`V0.6` 的起点不是继续补 `SystemEvent`、新 `Coordinator`、新页面栈或更多 Core 名词。

`V0.6` 的起点应该是平台 Action executor：

1. 平台如何执行 `TURN_SCREEN_OFF` / `WAKE_SCREEN`。
2. 执行成功或失败后，如何回到 `watch_core_commit_power_action()`。
3. F411、PC、LILYGO 如何各自实现执行层，但仍共享同一套 Power 合同。
4. 熄屏态下哪些输入能唤醒，哪些输入被丢弃或延后。

也就是说：

- `V0.5` 解决“谁负责决定”。
- `V0.6` 解决“平台怎么把这个决定真正做出来”。

---

## 7. 为什么这对后续学习很重要

这轮最大的学习沉淀，不是多写了几个类型，而是学会了三件更难的事：

1. 先审计真实代码，再决定下一步，而不是按想象中的空白系统规划。
2. 区分“共享合同缺口”和“平台实现缺口”。
3. 在还能运行的系统上做边界收口，而不是冲动重写。

如果没有这轮沉淀，后续很容易在 `V0.6` 再次犯两种错：

- 把平台执行问题又塞回 Core。
- 为了“看起来更完整”而重复发明已经存在的抽象。

---

## 8. 给 `V0.6` 的交接清单

进入 `V0.6` 前，默认继承以下前提：

- 不重做 `watch_core` 导航合同。
- 不重做 `PageState / PageIntent / Snapshot` 定义。
- 不重做最小 Power 合同。
- 不让 Adapter 重新拥有业务状态权威。
- 不让 Platform 成为策略源。

`V0.6` 第一批实现卡应围绕：

- 平台 Power executor
- F411 表冠与熄屏态输入门控
- PC / F411 / LILYGO 的执行回路对齐
- 平台执行后的回归与审计

而不是围绕：

- 再造一个“大总线”
- 再造一个“大状态机”
- 再补一轮抽象名词

---

## 9. 阶段结论

`V0.5` 到这里已经完成了它应完成的事：

- 共享合同从“能跑”提升到“可测试、可解释、可交接”。
- 学习重点从“会不会写模块”提升到“能不能判断边界和所有权”。
- `V0.6` 的起点已经被压缩到真正需要实现的平台执行层。

这就是 `V0.5` 对后续最大的价值。

# Magic Watch 架构冲突实验场总纲

> 状态：方向基线，允许根据实验结果持续修订  
> 路由类型：按需开发指南  
> 当前边界：Stage 00、Stage 01、Stage 02、Stage 03 与 Stage 04 已冻结；Stage 05 仅完成规划

## 1. 目的

架构冲突实验场不负责复刻 Magic Watch，也不以得到某套预定架构为目标。

它通过受控的需求变化和约束冲突，让项目所有者亲自判断：

- 当前写法是否真的开始变贵。
- 问题属于局部代码、View、状态所有权、时间顺序还是平台边界。
- 简单耦合、局部抽象和系统抽象各自要付出什么代价。
- 某个抽象应当现在引入、延迟引入、撤销，还是根本不需要。

成功标准不是最终代码像 Magic Watch，而是能够根据证据回答：

> 当前为什么值得多加一层，或者为什么此时应该忍住不重构？

## 2. Anti-goals

本实验场不追求：

- 完整手表功能或漂亮 UI。
- 最终架构一步到位。
- 复刻 Magic Watch 当前实现。
- 证明某个抽象必然正确。
- 代码量、目录数量或 Stage 数量。
- 真实硬件调试。
- 为未来需求提前预留接口。

## 3. 产品隔离

- 实验场使用独立的 PC LVGL + SDL 工程，不成为 Magic Watch 的候选产品分支。
- 实验代码不得直接复制回 Magic Watch。
- Magic Watch 的 Core、Adapter、合同类型和最终实现不得直接灌入实验场。
- 两者只共享需求经验、失败案例、判断方法和最终判断表。
- 实验中出现相似结构时，必须由当前需求压力推导，不能以“Magic Watch 已经这样做”为理由。

## 4. 核心原则

1. 需求压力先于抽象。
2. 简单耦合是合法方案，不以层数多少评价设计成熟度。
3. 每个 Stage 都允许得出“不重构”的结论。
4. 候选方案数量由问题决定，不机械要求三种。
5. 先用当前结构实现或推演，再判断修改压力是否真实存在。
6. 比较收益时必须同时记录认知、调试、接口和迁移成本。
7. 用户负责事前预测、方案选择和事后判断修正。
8. AI 可以补背景、机械实现、测试和反例，但不得提前宣布标准答案。
9. 失败案例必须服务真实问题，不为了课程效果强制制造崩溃。
10. Stage 结论只对当时需求和约束成立，不写成普遍真理。

每个 Stage 的复盘默认控制在 500～1000 字，只记录决策、修改、失败和代价。遇到真正影响后续判断的重要冲突时才允许扩写。

## 5. 固定实验流程

```text
冻结当前基线
-> 给出新需求和约束
-> 用户记录事前预测
-> 先用当前结构实现或推演
-> 观察真实修改压力
-> 判断是否需要抽象
-> 比较候选方案
-> 实施用户选择
-> 施加必要的反例
-> 记录收益、代价和判断修正
-> 冻结当前 Stage
```

用户每轮至少亲自完成：

- 一项状态或所有权判断。
- 一个关键处理函数或最小测试。
- 选择理由与风险预测。
- 结束后的判断修正。

不采用隐藏或加密的 AI 结论。用户的事前记录就是判断基线，最终以实际修改、运行结果和反例观察为证据。

## 6. Stage 记录模板

每个 Stage 的 `README.md` 只记录：

```text
## 新需求与约束
## 当前调用链与状态所有权
## 我的事前预测
## 候选方案与选择
## 实际修改范围
## 可观察失败或维护压力
## 收益、代价和新增风险
## 保留、撤销或延迟抽象的决定
## 我高估和低估了什么
```

可记录修改文件数、规则重复数、直接依赖 LVGL 的模块数、状态真相来源数、新增接口数和调用步骤增量。这些数字只帮助比较，不作为架构质量评分。

## 7. Stage 启动门

启动新 Stage 前必须确认：

- 上一阶段已经运行并冻结。
- 存在明确的新需求和约束。
- 需要通过代码变化才能观察问题。
- 当前问题不是仅靠解释就能解决的知识缺口。
- 后续 Stage 只有在前一 Stage 的实际观察证明存在相应需求压力时才能启动。

不得因为下方地图存在就自动创建下一阶段、代码目录或执行卡。

如果尚未观察到真实冲突，只能继续使用当前朴素结构增加需求或收集证据，不得升级架构。

## 8. Stage 停止门

冻结当前 Stage 前必须确认：

- 工程已经实际运行。
- 已记录用户的事前预测。
- 已记录真实修改范围。
- 已观察到收益、代价或“问题尚未出现”。
- 已决定保留、撤销或延迟抽象。
- 当前结论明确绑定本轮需求和约束。

未满足停止门时，不得把 Stage 写成完成，也不得规划下一阶段的实现。

## 9. 暂定冲突地图

以下只是假设清单，不是执行路线：

- 小需求下直接 callback 是否已经足够。
- UI 增长究竟只是 View 问题，还是业务边界问题。
- 多输入是否产生共享语义压力。
- 异步来源是否破坏 UI 所有权和事件顺序。
- 脱离 UI 后能否验证产品行为。
- 第二套 View 是否真正暴露业务规则复制。
- 动态数据是否形成多个真相来源。
- Power 失败是否破坏逻辑状态与硬件事实的一致性。
- 强制不重构后，现有结构是否仍然足够。
- 反向审计此前抽象，识别错误或过早设计。

地图可以重排、合并、删除或停止。任何后续阶段都必须重新经过启动门。

## 10. Stage 00 边界

Stage 00 只实现：

- Heart、Steps 两张卡。
- 点击卡片进入对应详情。
- Back 返回首页。
- 单 View、鼠标输入、同步执行。

允许：

- 直接 LVGL callback。
- `current_feature`。
- `show_home()` 和 `show_detail()`。

禁止：

- EventQueue、Coordinator、Adapter。
- PageState、PageIntent、Snapshot。
- XML、异步来源和跨平台预留。
- 为后续 Stage 预建接口或目录。

Stage 00 的目标是验证简单实现是否已经足够，不是故意写坏代码。

如果 Stage 00 没有暴露真实维护问题，下一阶段只能继续使用朴素写法增加需求。不得因为 UI 代码开始增长就立即拆层，必须先观察重复、修改扩散、状态冲突或测试困难。

## 11. 当前停止点

Stage 00 已完成并冻结：

- 实验工程位于仓库内的 `watch_arch_learning/`。
- runtime 只提供 LVGL 9.6 + SDL 启动与主循环。
- Stage 00 的关键直接行为由用户亲自接通。
- Stage 00 本身不包含为后续 Stage 预建的接口或目录。
- 不把暂定冲突地图写入自动执行队列。

Stage 01 使用 PC 标准输入输出替代 LVGL、SDL、触摸和显示对象，确认了显式页面状态、命令决策与输出表现的最小链路。它仍保持直接调用，没有预建 Intent、Core 或 Renderer。

Stage 02 只能增加一种明确的需求压力，继续使用直接结构观察后再判断是否需要抽象。

当前 Stage 02 选择的单一压力是“上下文相关导航”：

- 增加 App Menu、菜单选择与详情入口。
- 保留 Home 快捷入口，制造两条进入同一详情的真实路径。
- 观察 `back`、`next`、`prev`、`enter` 如何依赖当前页面和进入来源。
- 不同时加入第二输入、异步事件、设置数据或 UI 框架。

Stage 02 已确认页面状态、菜单选择和详情返回目标是三个不同事实。当前固定导航深度不需要页面栈；下一阶段必须引入新的单一压力，不能机械增加导航层级。

Stage 03 选择的单一压力是“第二种输入表示”：

- 保留终端语义命令。
- 新增 `key_next`、`key_prev`、`key_select`、`key_back` 模拟实体按键。
- 页面、导航状态与输出保持不变。
- 先观察直接接入造成的重复和硬件名称泄漏，不预设 Intent 或 Input Adapter。

用户已完成输入边界预测并选择方案 B。Stage 03 证明：

- 硬件名称 `key_*` 可以被隔离在翻译入口。
- 相同按键在不同页面含义不同，因此翻译层仍读取当前页面。
- 当前真正共享的仍是字符串命令语言，而不是最小内部动作语义。

因此 Stage 04 的单一压力不应是异步、队列或消抖，而应继续观察：
如果再来一个不想伪装成终端文本的调用入口，字符串命令是否已经变成隐式内部合同。

Stage 04 的第一版做法是：

- 新增一个脚本回放入口。
- 让它先以本地步骤语言表达行为。
- 再被迫翻译成既有命令字符串去复用 `handle_command()`。

这样能直接观察：当前系统真正共享的，是不是已经不是“输入源”，而是
`"menu"`、`"next"`、`"enter"`、`"back"` 这套命令字符串语言。

Stage 04 已进一步证明：

- 新入口天然更想表达步骤语义。
- 旧导航却只能消费字符串命令。
- 一旦新入口想表达更高层目标，就要自己补一段把目标拆成多次 `"next"` 和
  一次 `"enter"` 的中间逻辑。

因此，下一阶段若继续推进，最合理的唯一压力将是：

- 最小共享动作语义是否真的值得引入。

Stage 05 只规划这一个问题：

- 最小共享动作语义的候选集合是什么
- 它应该替代字符串命令的哪一层
- 如何验证它真的减少中间翻译，而不是只把字符串换成枚举名
